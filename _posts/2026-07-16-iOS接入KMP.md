## JDK环境安装

### 1. 验证是否安装JDK

```shell
/usr/libexec/java_home -V

The operation couldn’t be completed. Unable to locate a Java Runtime.
Please visit http://www.java.com for information on installing Java.
```

### 2. 安装JDK

- 访问 [adoptium]( https://adoptium.net/) 官网
- 选择 macOS 和想要的 JDK 版本
- 下载 `.pkg` 文件，双击安装

> 注意：建议安装`21`版本，最新版本会报错

### 3. 验证JDK安装是否成功

```shell
java -version
```

## 集成方式

### 本地集成

#### 直接集成

使用 `embedAndSignAppleFrameworkForXcode` 这个专门为 Xcode 量身定做的 Gradle 任务

1. 在 `build.gradle.kts` 中定义 iOS Target

   ```kotlin
   kotlin {
     ...
     
     iosArm64()
     iosSimulatorArm64()
     
     ...
   }
   ```

2. 在 Xcode 项目的 `Build Phases` 中添加 `New Run Script Phase`，填入如下内容并调整

   ```shell
   if [ "YES" = "$OVERRIDE_KOTLIN_BUILD_IDE_SUPPORTED" ]; then
       echo "Skipping Gradle build task invocation due to OVERRIDE_KOTLIN_BUILD_IDE_SUPPORTED environment variable set to \"YES\""
       exit 0
   fi
   cd "<Path to the root of the multiplatform project>"
   ./gradlew :<Shared module name>:embedAndSignAppleFrameworkForXcode
   ```

   * 在 `cd` 命令中，需指定您的 KMP 项目根目录的路径，例如：`$SRCROOT/..`
   * 在 `./gradlew` 命令中，需指定共享模块的名称，例如：`:shared` 或 `:composeApp`

3. 关闭 `Based on dependency analysis` 选项

   这样就能确保 Xcode 在每次构建时都会运行该脚本，并且不会每次出现缺少输出依赖项的警告

4. 将该脚本的位置置于 `Compile Sources` 之上

5. 在 `Build Settings` 下关闭 `User Script Sandboxing` 选项

#### CocoaPods集成

1. 找到 KMP 项目根目录下的 `gradle/libs.versions.toml` 文件，在 `[plugins]` 下添加插件：

   ```toml
   kotlinCocoapods = { id = "org.jetbrains.kotlin.native.cocoapods", version.ref = "kotlin" }
   ```

2. 找到 KMP 项目根目录下的 `build.gradle.kts` 文件，在 `plugins {}` 中添加如下代码：

   ```kotlin
   alias(libs.plugins.kotlinCocoapods) apply false
   ```

3. 找到 `shared` 模块的 `build.gradle(.kts)` 文件，在 `plugins {}` 中添加 CocoaPods 插件：

   ```kotlin
   alias(libs.plugins.kotlinCocoapods)
   ```

4. 在 `kotlin {}` 下添加 `cocoapods` 模块，然后配置 `podspec` 相关的版本、简介、主页等信息：

   ```kotlin
   cocoapods {
       name = "RuyiShared"
       summary = "ruyi-app"
       homepage = "http://gitlab.mx.com/kmp/ruyi-app.git"
       version = libs.versions.versionName.get().toString()
       ios.deploymentTarget = "14"
       framework {
           baseName = "RuyiShared"
           isStatic = true
   
         	// 导出需要给 iOS 使用的模块
   				// 这种方式有副作用：会导出子模块的所有公共类，包括内部实现细节，可能导致头文件非常臃肿，且不同子模块如果有同名类会冲突
         	// 更好的方式是在 shared 模块的 commonMain 下创建一个类来封装需要导出给 iOS 使用的类和方法
         	// 只能导出使用 api() 依赖的模块
           export(projects.kmpCommon)
           export(projects.kmpCore)
   
           export(projects.appCommon.core)
           export(projects.appCommon.datasource)
           export(projects.appCommon.domain)
           export(projects.appCommon.interactor)
           export(projects.appCommon.ui)
       }
   }
   ```

   > 只能导出使用 `api()` 依赖的模块
   >
   > https://kotlinlang.org/docs/multiplatform/multiplatform-build-native-binaries.html#export-dependencies-to-binaries

   | 配置项       | 核心作用                                                     | 作用于谁               | 对 iOS 端的影响                                              |
   | :----------- | :----------------------------------------------------------- | :--------------------- | :----------------------------------------------------------- |
   | **`api`**    | 在 **Gradle 编译时**，将模块 A 的依赖传递给依赖模块 A 的其他模块。 | Kotlin 编译器和 Gradle | **间接影响**：保证你的 KMP 模块代码自身能正常编译通过。      |
   | **`export`** | 在 **生成 iOS Framework 时**，将其它模块的 API 也**显式地**包含进最终产物，供 iOS 调用。 | Kotlin/Native 编译器   | **直接影响**：直接影响 iOS App 最终能看到并调用哪些类和 API。 |

   | 特性               | `api`                                                      | `implementation`                         |
   | :----------------- | :--------------------------------------------------------- | :--------------------------------------- |
   | **依赖传递**       | ✅ 会传递给下游模块                                         | ❌ 不会传递给下游模块                     |
   | **下游模块可见性** | 下游模块能访问该依赖中的类型                               | 下游模块无法访问该依赖中的类型           |
   | **编译隔离**       | 弱（依赖变化会触发下游重新编译）                           | 强（依赖变化只重新编译当前模块）         |
   | **构建速度影响**   | 较慢（级联编译）                                           | 较快（隔离编译）                         |
   | **模块封装性**     | 低（公开了依赖细节）                                       | 高（隐藏内部实现）                       |
   | **推荐使用场景**   | 依赖的类型出现在**当前模块的公开 API**（参数、返回类型等） | 依赖**仅用于模块内部实现**，不暴露给外部 |

   > **默认使用 `implementation`，只有当你的公开函数或属性直接暴露了该依赖的类型时，才使用 `api`**
   >
   > **如果需要使用 `export` 导出给 iOS 端使用，则必须使用 `api`**

5. 使用更新后的 Gradle 文件更新项目，更新完成后在当前模块根目录下会生成一个 `podspec` 文件

   ```ruby
   Pod::Spec.new do |spec|
       spec.name                     = 'RuyiShared'
       spec.version                  = '9.3.4'
       spec.homepage                 = 'http://gitlab.mx.com/kmp/ruyi-app.git'
       spec.source                   = { :http=> ''}
       spec.authors                  = ''
       spec.license                  = ''
       spec.summary                  = 'ruyi-app'
       spec.vendored_frameworks      = 'build/cocoapods/framework/RuyiShared.framework'
       spec.libraries                = 'c++'
       spec.ios.deployment_target    = '14'
       if !Dir.exist?('build/cocoapods/framework/RuyiShared.framework') || Dir.empty?('build/cocoapods/framework/RuyiShared.framework')
           raise "
           Kotlin framework 'RuyiShared' doesn't exist yet, so a proper Xcode project can't be generated.
           'pod install' should be executed after running ':generateDummyFramework' Gradle task:
               ./gradlew :shared:generateDummyFramework
           Alternatively, proper pod installation is performed during Gradle sync in the IDE (if Podfile location is set)"
       end
       spec.xcconfig = {
           'ENABLE_USER_SCRIPT_SANDBOXING' => 'NO',
       }
       spec.pod_target_xcconfig = {
           'KOTLIN_PROJECT_PATH' => ':shared',
           'PRODUCT_MODULE_NAME' => 'RuyiShared',
       }
       spec.script_phases = [
           {
               :name => 'Build RuyiShared',
               :execution_position => :before_compile,
               :shell_path => '/bin/sh',
               :script => <<-SCRIPT
                   if [ "YES" = "$OVERRIDE_KOTLIN_BUILD_IDE_SUPPORTED" ]; then
                       echo "Skipping Gradle build task invocation due to OVERRIDE_KOTLIN_BUILD_IDE_SUPPORTED environment variable set to \"YES\""
                       exit 0
                   fi
                   set -ev
                   REPO_ROOT="$PODS_TARGET_SRCROOT"
                   "$REPO_ROOT/../gradlew" -p "$REPO_ROOT" $KOTLIN_PROJECT_PATH:syncFramework \
                       -Pkotlin.native.cocoapods.platform=$PLATFORM_NAME \
                       -Pkotlin.native.cocoapods.archs="$ARCHS" \
                       -Pkotlin.native.cocoapods.configuration="$CONFIGURATION"
               SCRIPT
           }
       ]
       spec.resources = ['build/compose/cocoapods/compose-resources']
   end
   ```

6. 更新 `Podfile` 文件

   ```ruby
   target 'iosApp' do
   	# KMP 生成的 framework  
     pod 'shared', :path => '../shared'
     # 其他依赖
     pod 'RxSwift', '6.6.0'
     pod 'RxCocoa', '6.6.0'
     pod 'SnapKit', '5.7.1'
   end
   ```

> 目前 KMP 生成的 framework 是 Objective-C 的形式，Swift framework 的形式处于实验当中，目前还不支持 CocoaPods 接入
>
> https://kotlinlang.org/docs/native-swift-export.html#current-limitations

## Podspec中的2个Gradle Task

### generateDummyFramework

在没有真正编译 Kotlin 代码的情况下，先生成一个空的 `.framework` 骨架文件，让 CocoaPods 的 `pod install` 能正常通过，不报错。

看 `RuyiShared.podspec` 第 12-17 行，这正好就是检查机制：

```
raise "Kotlin framework 'RuyiShared' doesn't exist yet..."
```

当 `build/cocoapods/framework/RuyiShared.framework` 不存在或为空时，`pod install` 会抛出这个错误，并明确提示你先执行：

```bash
./gradlew :shared:generateDummyFramework
```

工作原理：

1. 在 `build/cocoapods/framework/` 目录下**创建**一个 `RuyiShared.framework` 目录
2. 在里面放置一个**空的/最小化的**二进制文件（dylib）和必要的 Info.plist
3. 这个 framework **只包含占位符号**，没有任何实际代码

所以它本质上是**哄骗 CocoaPods 的"空壳"**。

### syncFramework

触发 Gradle 编译 Kotlin/Native 代码生成真正的 `RuyiShared.framework`，在 Xcode 每次编译项目时自动运行

该脚本等价于手动执行：

```bash
./gradlew :shared:syncFramework \
    -Pkotlin.native.cocoapods.platform=... \
    -Pkotlin.native.cocoapods.archs="..." \
    -Pkotlin.native.cocoapods.configuration=...
```

三个 `-P` 参数把 Xcode 的编译信息传给 Gradle，确保 Kotlin 编译出**正确的架构和配置**

| 环境变量         | 示例值                         | 作用                |
| ---------------- | ------------------------------ | ------------------- |
| `$PLATFORM_NAME` | `iphoneos` / `iphonesimulator` | 指定编译目标平台    |
| `$ARCHS`         | `arm64` / `x86_64`             | 指定编译的 CPU 架构 |
| `$CONFIGURATION` | `Debug` / `Release`            | 指定编译配置        |

> Kotlin CocoaPods 插件默认只区分两种 CONFIGURATION：
>
> * `Debug`：有调试符号，无优化
> * 非`Debug`：无调试符号，有优化

一句话总结：

在编译 Swift 代码之前，自动调用 `./gradlew :shared:syncFramework` 去编译 Kotlin/Native 生成 `RuyiShared.framework`，确保 Xcode 能用上最新的 Kotlin 代码，同时根据 Xcode 当前是**模拟器/真机**、**Debug/Release** 来编译对应版本。

## 共享模块组织方式

### 单一模块

项目中只包含一个共享的模块

* 优点：
  * 简洁的设计仅包含一个模块，这能减轻认知负担。您无需考虑将功能放置何处，也无需思考如何将功能合理地划分成不同的部分。
  * 作为起点来说效果很好。
* 缺点：
  * 随着共享模块的增大，编译时间也会相应增加。
  * 这种设计不允许存在独立的功能模块，也不允许仅依赖应用程序所必需的功能来进行开发。

### 多模块

根据功能将共享模块划分成多个

* 优点：
  * 共享代码的职责分离。
  * 更强的可扩展性。
* 缺点：
  * 更复杂的设置，包括伞状框架（`umbrella framework`）的设置。
  * 在各个模块之间实现了更复杂的依赖关系管理。

> * iOS 应用程序不要使用多个 KMP 生成的框架（framework），这样会导致编译时出现重复符号的问题，这是因为每个 KMP 框架都会包含一份完整的依赖库副本
> * iOS 应用程序可以依赖由 KMP 生成的一个框架（framework）。当您使用多个模块时，您需要**添加一个额外的模块**（称为`伞形模块（umbrella module）`），该模块依赖于您正在使用的所有模块，然后您还需要配置一个包含所有模块的框架（称为`伞形框架（umbrella framework）`）。
> * 安卓项目既可以依赖这个`伞形模块（umbrella module）`，也可以依赖单独的功能模块

https://touchlab.co/multiple-kotlin-frameworks-in-application/

## iOS中KMP代码可见性

| 场景                                  | 能否在 iOS 使用 | 说明                                     |
| ------------------------------------- | --------------- | ---------------------------------------- |
| `shared` 模块中的类型                 | ✅ 直接可用      | 自动导出                                 |
| 子模块（network/datastore等）中的类型 | ❌ 默认不可用    | 需要包装类桥接或使用`api` + `export`导出 |
| 通过 `shared` 包装类暴露的子模块类型  | ✅ 可用          | 编译器会连带导出                         |

> 模块名不一定非得叫 `shared`，这个随便起

## 万达电影iOS App接入KMP

### 脚本+同级目录

1. 在 iOS 项目根目录下新建1个配置文件 `kmp_git_component_cfg.cfg` ，内容如下：

   ```
   git@gitlab.mx.com:kmp/ruyi-app.git 1.0.0 ruyi-app
   ```

2. 在项目根目录下新建一个脚本文件 `kmp_git_install_all.sh`，用来拉取并同步上面配置文件列出来的仓库，成功后，在项目同级目录下（脚本文件所在目录的上一级目录）多了1个文件夹，对应的就是配置文件中列出的仓库，目前只有一个：

   ```shell
   # 目录
   ruyi-app
   ```

   > `kmp_git_install_all.sh` 还会拉取 ruyi-app 依赖的仓库

3. 新建一个脚本文件 `kmp_generate_dummy_framework.sh`，使用 `gradle` 提供的 Task 来生成占位 `framework`，核心内容如下：

   ```shell
   ······
   # 核心命令
   ./gradlew :shared:generateDummyFramework
   ······
   ```

   > `shared` 是模块名，根据自己需要生成 `framework` 的模块进行调整

4. 修改 `install.sh` 脚本，在开头添加如下代码，确保执行 `pod install` 之前已经拉取 KMP 代码并生成可供 Xcode 项目使用的占位 `framework`

   ```shell
   # 拉取并同步 kmp 库 && 生成占位 framework
   ./kmp_git_install_all.sh
   
   # 剩下的内容
   ......
   ```

5. 在 `Podfile` 中添加依赖的库

   ```ruby
   pod 'RuyiShared', :path => '../ruyi-app/shared'
   ```

6. 在需要依赖 KMP 项目的组件 `podspec` 文件中添加依赖

   ```ruby
   s.dependency 'RuyiShared'
   ```

7. 执行 `install.sh` 脚本集成 KMP 提供的 `framework`

### Git Submodule（暂时不用）

1. 在 iOS 仓库中添加 KMP 子模块

   ```ruby
   cd ios-project
   git submodule add https://github.com/your-team/kmp-shared.git KmpShared
   ```

   此时 iOS 仓库根目录下会多出一个 `.gitmodules` 文件和一个 `KmpShared` 文件夹（里面是 KMP 源码）

2. iOS 项目引用子模块中的源码

   通过 CocoaPods 的 `:path` 指向该目录

3. 日常协作流程

   1. 拉取最新 KMP 代码

      ```shell
      git pull                      # 拉取主仓库更新（可能包含子模块指针变化）
      git submodule update --init --recursive
      ```

   2. 修改 KMP 代码

      进入 `KmpShared` 目录，正常修改、提交、推送（到 KMP 仓库）

   3. 记录子模块指针变更

      修改并推送完 KMP 仓库后，回到主仓库根目录

      ```shell
      git add KmpShared
      git commit -m "更新 KMP 子模块指针"
      git push
      ```

   4. 安卓团队同步

      安卓团队执行 `git pull` + `git submodule update` 即可获得最新的 KMP 代码

**优点：**

* **两个团队工作流对称**，都是标准的 Git 操作，不需要学习新工具
* **版本明确**：每个主仓库锁定的 KMP 版本就是子模块的 commit hash，避免了“我改了但你没拉到”的问题
* **CI/CD 友好**：只需在构建前加一步 `git submodule update` 即可

**缺点：**

* 每个团队成员需要了解 `submodule` 的基本命令（`update`、`add`、`--remote` 等），有一定学习成本
* 容易忘记“先提交子模块再提交主仓库”的顺序，导致别人拉取后指针不匹配。**可以通过团队规范或 Git Hook 来避免**

## 万达电影iOS App使用KMP开发

### 共享UI（ComposeUI）+ 共享逻辑

如果 iOS 端使用 ComposeUI 开发好的页面，需要使用 `ComposeUIViewController` 进行包装一下，函数定义如下：

```kotlin
fun ComposeUIViewController(content: @Composable () -> Unit): UIViewController =
    ComposeUIViewController(configure = {}, content = content)
```

函数参数是一个 `@Composable` 注解修饰的 lambda 表达式

操作步骤：

1. 在 `ruyi-app` 这个 KMP 项目中找到 `shared` 模块，在 `src/iosMain` 目录下找到 `ComposeUIViewControllerFactory.kt` 这个文件，在其中添加需要在 iOS 端使用的 ComposeUI 开发好的页面：

   ```kotlin
   fun demoViewController() = ComposeUIViewController { SampleMainScreen() }
   ```

2. 回到 Xcode，在需要使用 ComposeUI 开发好的页面的地方导入头文件并使用

   ```swift
   import RuyiShared
   
   
   let kmpVC = ComposeUIViewControllerFactoryKt.demoViewController()
   navigationController?.pushViewController(kmpVC, animated: true)
   ```

   > 注意：这里定义的函数是顶层函数，没有被类包裹，所以在 iOS 测使用的时候是使用 `文件名+Kt.xxx()` 来调用函数

### 原生UI + 共享逻辑

以 MVVM 为例，iOS 端负责 `View` 层，KMP 端负责 `ViewModel` 和 `Model` 层

由于 KMP 使用 `Flow` 来进行数据流的传递，iOS 端无法直接使用，所以需要对 KMP 端的 `ViewModel` 进行包装

操作步骤：

1. 在 `ruyi-app` 这个 KMP 项目中找到 `shared` 模块，在 `src/iosMain` 目录下找到 `ViewModelWrapperFactory.kt` 这个文件，在其中添加需要暴漏给 iOS 端使用的 `ViewModel` 包装器：

   ```kotlin
   fun createProductsViewModelWrapper(): ViewModelWrapper<ItemEvent, ItemState, ItemAction> =
       viewModelWrapperOf<ProductsViewModel, ItemEvent, ItemState, ItemAction>()
   ```

   * `ViewModelWrapper` 定义好的 `ViewModel` 包装器，iOS 端使用它来进行后续操作
   * `viewModelWrapperOf` 定义好的函数，用来创建 `ViewModel` 包装器
   * `ProductsViewModel` iOS 端使用的 `ViewModel`
   * `ItemEvent`、`ItemState`、`ItemAction` 是定义 `ViewModel` 时传递的泛型类型

   > 这里的 `ViewModel` 必须继承自 `BaseViewModel`

2. 回到 Xcode，创建一个 `ViewController`，添加依赖并创建 `ViewModel` 包装器

   ```swift
   import RuyiShared
   
   // 创建 ViewModel 包装器
   private let wrapper = ViewModelWrapperFactoryKt.createProductsViewModelWrapper()
   ```

3. 定义绑定状态的方法

   ```swift
   private func setupBindings() {
       // 订阅 Kotlin ViewModel 的 State 变化
       wrapper.observeState { [weak self] state in
           guard let self else { return }
           updateUI(with: state)
       }
   
       // 订阅错误
       wrapper.observeError { [weak self] message in
           guard let self else { return }
           handleError(message)
       }
   
       // 订阅单次 Action（例如导航）
       wrapper.observeAction { [weak self] action in
           guard let self else { return }
           handleAction(action)
       }
   }
   ```

   > 具体实现看 Demo

4. 刷新数据及上拉加载更多

   ```swift
   // 刷新数据
   private func loadData() {
       wrapper.setEvent(event: ItemEvent.Refresh())
   }
   
   // 加载更多
   private func loadMoreData() {
       wrapper.setEvent(event: ItemEvent.LoadMore())
   }
   ```

5. 在 `deinit` 中释放资源，防止内存泄漏

   ```swift
   deinit {
       wrapper.dispose()
   }
   ```

## SKIE（Swift Kotlin Interface Enhancer）

### 介绍

KMP 为 Swift 提供的接口是 Objective-C。尽管这常常被指责是导致 Kotlin 特性缺失的原因，但实际情况是，Kotlin 和 Swift 实质上是两种不同的语言。为了将现代 Kotlin 的特性“嫁接”到 Swift 中，并提供一个更友好、更易用的面向 Swift 的 API，我们构建了 SKIE。

SKIE 将一些现代的 Kotlin 语言特性与 Swift 对应的功能进行了对接，并为 Kotlin 的协程提供了与 Swift 异步结构的自动双向支持。

对于新项目，我们强烈建议默认启用 SKIE 功能。对于现有的代码库，请遵循 SKIE 迁移指南。SKIE 的设计旨在尽可能实现无缝替换，但不可避免地会改变类型，因此如果将 SKIE 应用到整个项目中，现有的代码可能无法正常运行。您可以根据需要逐步应用 SKIE。

> https://skie.touchlab.co/
