# 2026-07-30 KMP 页面开发指南 —— 勋章墙实现

> 本文只记录「勋章墙」这一个功能的完整实现链路：接口 → 数据层 → 领域层 → UI 层。
> 涉及模块：`app-common/data`、`app-common/domain`、`app-main/mine`。
> 接口：`/medal/user_medal_list.api`

## 整体数据流

```
后端 JSON (/medal/user_medal_list.api)
   │
   ▼ ① 数据层 MedalApi            拿到 MedalListDTO（后端形状，字段可空）
   ▼ ② 数据层 MedalListMapper     DTO → MedalList（领域形状，清洗可空、聚合字段）
   ▼ ③ 数据层 MedalRepositoryImpl 封装成 Result<MedalList>
   ▼ ④ 领域层 MedalRepository(接口) / MedalWallUseCase(用例)
   ▼ ⑤ UI 层 MedalWallViewModel → MedalWallScreen（Compose 共用）
```

---

## 第一步：数据层（app-common / data / medal）

数据层位于 `app-common/data/src/commonMain/kotlin/com/app/common/data/medal/`，分 4 个文件。

### 1. `api/MedalApi.kt` —— 接口地址与网络请求
负责"怎么调网络"：拼 URL、发请求，直接拿回 `MedalListDTO`。

```kotlin
interface MedalApi {
    companion object {
        const val USER_MEDAL_LIST = "/medal/user_medal_list.api"
    }
    suspend fun getUserMedalList(): Response<MedalListDTO>
}

internal class MedalApiImpl(
    private val client: HttpClient,
    private val apiHost: Host
) : MedalApi {
    override suspend fun getUserMedalList(): Response<MedalListDTO> {
        return client.get {
            url { takeFrom(apiHost.user); encodedPath += MedalApi.USER_MEDAL_LIST }
        }.body()
    }
}
```

### 2. `dto/MedalListDTO.kt` —— 网络数据（后端契约）
与后端 JSON 字段一一对应，用 `@Serializable` 做反序列化。**字段跟随后端，且大多可空。**

```kotlin
@Serializable
data class MedalListDTO(
    @SerialName("avatarUrl") val avatarUrl: String? = null,
    @SerialName("wallWriting") val wallWriting: String? = null,
    @SerialName("medalEntry") val medalEntry: List<WallMedaliItemDTO>? = null
)

@Serializable
data class WallMedaliItemDTO(
    @SerialName("medalId") val medalId: Int? = null,
    @SerialName("medalUrl") val medalUrl: String? = null,
    @SerialName("medalName") val medalName: String? = null,
    @SerialName("medalDesc") val medalDesc: String? = null,
    @SerialName("canReceive") val canReceive: Boolean = false,
    @SerialName("medalStatus") val medalStatus: Boolean = false,
    @SerialName("totalEquity") val totalEquity: Int = 0,
    @SerialName("receiveEquity") val receiveEquity: Int = 0,
    @SerialName("avatarFrameUrl") val avatarFrameUrl: String? = null
)
```
> 注：`WallMedaliItemDTO` 中 `Medali` 的 `i` 小写是沿用 iOS（wanda-swift）历史命名，DTO 直接照搬，mapper 转领域时重命名为规范的 `WallMedaliItem`。

### 3. `mapper/MedalListMapper.kt` —— DTO → 领域（关键工序）
负责拆信封、分拣、清洗：把可空压成安全默认值，并按 UI 需要重新聚合字段。

```kotlin
fun MedalListDTO.toDomain(): MedalList = MedalList(
    userInfo = MedalUserInfo(
        avatar = avatarUrl.orEmpty(),
        signature = wallWriting.orEmpty()
    ),
    items = medalEntry?.map { it.toDomain() }.orEmpty()
)

fun WallMedaliItemDTO.toDomain(): WallMedaliItem = WallMedaliItem(
    medalId = medalId ?: 0,
    medalUrl = medalUrl.orEmpty(),
    medalName = medalName.orEmpty(),
    medalDesc = medalDesc.orEmpty(),
    receiveEquity = receiveEquity,
    totalEquity = totalEquity,
    canReceive = canReceive,
    medalStatus = medalStatus,
    avatarFrameUrl = avatarFrameUrl.orEmpty()
)
```

### 4. `repository/MedalRepositoryImpl.kt` —— 仓库实现（对外入口）
把"调 API + 转领域"封装，对外只暴露领域模型 `Result<MedalList>`。

```kotlin
class MedalRepositoryImpl(private val api: MedalApi) : MedalRepository {
    override suspend fun getUserMedalList(): Result<MedalList> {
        return safeApiCall {
            api.getUserMedalList().converterResult {
                Result.Success(this?.toDomain() ?: MedalList())
            }
        }
    }
}
```

## 第二步：领域层（app-common / domain / medal）

领域层位于 `app-common/domain/src/commonMain/kotlin/com/app/common/domain/mine/medal/`，**只认业务模型，不知道网络/DTO 的存在**。

### 1. `MedalList.kt` —— 领域模型（业务契约）
按页面展示结构组织，字段不可空、带默认值，并标注 `@Stable`（Compose 稳定）。

```kotlin
@Stable
data class MedalList(

    val items: List<WallMedaliItem> = emptyList(),          // 勋章列表（三列网格）
    val userInfo: MedalUserInfo = MedalUserInfo()           // 顶部用户信息

@Stable
data class WallMedaliItem(

    val medalUrl: String = "",
    val medalName: String = "",
    val medalDesc: String = "",
    val receiveEquity: Int = 0,
    val totalEquity: Int = 0,
    val canReceive: Boolean = false,
    val medalStatus: Boolean = false,
    val avatarFrameUrl: String = ""

@Stable
data class MedalUserInfo(
    val avatar: String = "",
    val nickname: String = "",
```

### 2. `repository/MedalRepository.kt` —— 仓库接口（抽象）
领域层只定义接口，不关心实现来自网络还是本地。

```kotlin
interface MedalRepository {
    suspend fun getUserMedalList(): Result<MedalList>
}
```

### 3. `usecase/MedalWallUseCase.kt` —— 业务用例
把"取勋章墙数据"封装成单一业务动作，ViewModel 通过它拿数据。

```kotlin
class MedalWallUseCase(private val repository: MedalRepository)
    : BaseUseCase<Unit, MedalList>() {
    override suspend fun execute(params: Unit): Result<MedalList> {
        return repository.getUserMedalList()
    }
}
```

#### UseCase 在架构里的位置
UseCase 是领域层对外暴露的**唯一业务入口**。它夹在 Repository（数据来源）和 ViewModel（UI 状态）之间，职责是：
- **屏蔽数据来源**：ViewModel 只认 `MedalWallUseCase`，不关心数据来自网络、数据库还是 mock。
- **承载业务逻辑**：把多个 Repository 的结果组合、做校验、做错误降级，都放在这里，而不是塞进 ViewModel 或 UI。

#### 它继承的 BaseUseCase 提供了什么
`BaseUseCase`（`app-common/core`）采用**模板方法模式**，已经帮你封装好了通用流程，子类只需关心业务本身：
- 自动处理 Loading 状态（开始/结束进度条）；
- 自动检测网络异常并转为 `ApiError.Network`；
- 统一预解析 HTTP 错误码（401→Auth、429→Limit）与业务错误码；
- 把 `ApiResult` 统一映射成 `DataState`（即 UI 能直接消费的 `UIComponent.Network` / `Error` / `Empty` 等）。

所以子类通常只需要实现 `execute(params)` 返回业务数据即可。

#### 为什么勋章墙的 UseCase 这么"简单"
`MedalWallUseCase` 只有一个 Repository 依赖、没有参数、也没有额外逻辑，因为勋章墙就是"一次请求拿一个列表"。这是 UseCase 的**最小形态**。

对照项目里其它用例，可以看到 UseCase 能做的事远不止转发，举两个例子（说明"简单"只是当前需求决定，不是框架限制）：

**① 组合多个 Repository** —— `TemuHomeUseCase`（首页推荐）
它同时依赖 `TemuRepository` 和 `ExtraRepository`，在一个 `execute` 里并发/顺序拉取推荐列表、活动列表、Banner，再聚合成一个 `TemuHomeData` 返回给 UI。这就是 UseCase 做"数据编排"的典型场景。

```kotlin
class TemuHomeUseCase(
    private val repo: TemuRepository,
    private val extraRepo: ExtraRepository
) : BaseUseCase<TemuHomeRequest, TemuHomeData>() {
    override suspend fun execute(params: TemuHomeRequest): Result<TemuHomeData> {
        val rcmdList = repo.loadHomeRcmdList(params.rmcdRequest)
        val list = repo.loadHomeList(params.listRequest)
        val banner = extraRepo.getCommonExtra(params.bannerRequest)
        return Result.Success(TemuHomeData(
            if (rcmdList is Result.Success) rcmdList.data.recommendList else emptyList(),
            if (list is Result.Success) list.data.activityList else emptyList(),
            if (banner is Result.Success) banner.data.objects else emptyList()
        ))
    }
}
```

**② 前置校验 + 错误降级** —— `FeedbackSubmitUseCase`（反馈提交）
它在 `validate()` 里做提交前的内容校验（空、超长直接返回 `Error.Business` 拦截）；在 `execute()` 里用 `.map(...)` 把底层失败转成更友好的业务文案，并校验返回的 `feedbackCode` 是否非空。这是 UseCase 做"业务规则 + 错误语义化"的例子。

```kotlin
class FeedbackSubmitUseCase(private val repo: FeedbackRepository)
    : BaseUseCase<FeedbackSubmitParam, FeedbackSubmit>() {

    override suspend fun validate(params: FeedbackSubmitParam): Error? {
        if (params.feedbackContent.trim().isEmpty())
            return Error.Business(message = "提交内容不能为空")
        else if (params.feedbackContent.trim().length > 500)
            return Error.Business(message = "提交内容不能超过500字")
        return super.validate(params)
    }

    override suspend fun execute(params: FeedbackSubmitParam): Result<FeedbackSubmit> {
        return repo.submitFeedback(params).map(
            onFailure = { it.toBusiness(message = "反馈失败，请重试", useBusinessMessage = true) },
            onSuccess = {
                if (it.data.feedbackCode.isNotEmpty()) it
                else Result.Failure(Error.Business(message = "反馈失败，请重试"))
            }
        )
    }
}
```

#### 勋章墙 UseCase 未来可以这样扩展
如果后续勋章墙需求变复杂，可以直接在本文件里加逻辑，而不用动 ViewModel/UI：
- 想校验"未登录不请求" → 覆盖 `validate()`（类似 Feedback）；
- 想同时拼一个"勋章分类"接口 → 注入第二个 Repository，在 `execute` 里组合（类似 Temu）；
- 想自定义空页面文案 → 覆盖 `mapErrorToState()` 返回 `ErrorStrategy.Custom`。

## 第三步：UI 层（app-main / mine / medal）

### 1. `MedalWallViewModel.kt` —— 状态与事件
继承 `BaseViewModel`，用 `MedalWallState` 持有领域模型 `MedalList`，并在拿到数据后算出已领取/总权益数。

```kotlin
class MedalWallViewModelImpl(private val medalWallUseCase: MedalWallUseCase)
    : MedalWallViewModel() {

    init { setEvent(MedalWallEvent.LoadData) }

    override fun initialState() = MedalWallState()

    override fun onTriggerEvent(event: MedalWallEvent) {
        when (event) {
            is MedalWallEvent.LoadData -> loadMedalWallData()
        }
    }

    private fun loadMedalWallData() {
        executeUseCase(useCase = medalWallUseCase, params = Unit,
            onSuccess = { data ->
                val received = data.items.sumOf { it.receiveEquity }
                val total = data.items.sumOf { it.totalEquity }
                update { copy(medalList = data, receivedCount = received, totalCount = total) }
            })
    }
}

// 状态定义
data class MedalWallState(
    val isLoading: Boolean = false,
    val medalList: MedalList = MedalList(),
    val receivedCount: Int = 0,
    val totalCount: Int = 0
) : ViewState
```

### 2. `MedalWallScreen.kt` —— Compose 页面（共用）
纯 Compose 代码（`commonMain`），通过 `koinViewModel()` 取 ViewModel，直接消费 `state.medalList` 渲染顶部用户信息、三列勋章网格、可领取角标等。关键片段：

```kotlin
@Composable
fun MedalWallScreen(
    onBack: () -> Unit = {},
    onMedalClick: (Int) -> Unit = {},
    viewModel: MedalWallViewModel = koinViewModel()
) {
    val state by viewModel.state.collectAsState()
    Theme {
        DefaultScreenUI(
            popup = onBack,
            progressBarState = if (state.isLoading) ProgressBarState.ScreenLoading else ProgressBarState.Idle,
            onAction = { actionId ->
                when (actionId) {
                    UIComponent.Action.RETRY -> viewModel.setEvent(MedalWallViewModel.MedalWallEvent.LoadData)
                }
            },
            errors = viewModel.errors
        ) { innerPadding ->
            MedalWallContent(state = state, innerPadding = innerPadding, onMedalClick = onMedalClick)
        }
    }
}
```

页面渲染要点（对应领域模型字段）：
- **顶部 Header**：`userInfo.avatar`（头像）、`userInfo.signature`（签名，为空时回退文案"您有 X 个勋章被点亮"）。
- **三列网格**：`medalList.items.chunked(3)` 每行 3 个，`MedalGridItem` 渲染 `medalUrl` / `medalName` / `receiveEquity/totalEquity`。
- **可领取角标**：`item.canReceive` 为 true 时显示"可领取"红标。
- **点击**：`onMedalClick(item.medalId)` 跳转勋章详情。

## 第四步：依赖注入与平台入口（把勋章墙"挂"进项目）

前面三层只是"写好了组件"，要让它们真正跑起来、且能在 Android/iOS 共用，还需要两处接入改动。

### 1. `data/DataModule.kt` —— Koin 依赖注入注册
`dataModule`（Koin `module`）负责把所有实现类绑定成单例。勋章墙新增了 3 条绑定：

```kotlin
// Repository 实现（单例）
single<MedalRepository> { MedalRepositoryImpl(get()) }   // 第 77 行
// ApiService（单例）
single<MedalApi> { MedalApiImpl(get(), get()) }          // 第 91 行
// UseCase（单例）
single { MedalWallUseCase(get()) }                        // 第 103 行
```

`single { ... }` 表示全局单例；`get()` 是 Koin 的自动按类型注入。三级依赖链是：
`MedalApiImpl`（被 `MedalRepositoryImpl` 依赖）→ `MedalRepositoryImpl`（被 `MedalWallUseCase` 依赖）→ `MedalWallUseCase`（被 ViewModel 依赖）。
只要注册了这三条，ViewModel 就能通过 `koinViewModel()` 自动拿到 `MedalWallUseCase`，无需手动 new。

> 说明：`DataModule` 里还注册了 feedback / temu / upload 等其它模块，勋章墙只是其中新增的一小撮。所有模块共用同一份 `dataModule`，统一初始化。

### 2. `MineModuleCompose.kt` —— iOS 平台入口（ViewController 桥接）
KMP 的 `commonMain` 里 `MedalWallScreen` 是纯 Compose 函数，iOS 不能直接 push 一个 Compose 函数，需要用 `ComposeUIViewController` 把它包成 iOS 的 `UIViewController`。勋章墙新增了：

```kotlin
/**
 * 勋章墙页面
 * @param onBack 返回/关闭回调（由 wanda-swift 处理 pop）
 */
fun medalWallViewController(
    onBack: () -> Unit = {},
    onMedalClick: (Int) -> Unit = {},
    onScrollOffsetChanged: (Double) -> Unit = {},
    topInset: Double = 0.0
) = ComposeUIViewController {
    MedalWallScreen(
        onBack = onBack,
        showTopBar = false,
        onMedalClick = onMedalClick,
        onScrollOffsetChanged = { onScrollOffsetChanged(it.toDouble()) },
        topInset = topInset.toFloat()
    )
}
```

iOS 侧的 `wanda-swift` 通过调用 `medalWallViewController(...)` 拿到这个控制器并 push 进导航栈。
- `onBack`：返回事件交给原生处理 pop；
- `onMedalClick(medalId)`：点击勋章跳转，回调给原生决定去哪个详情页；
- `onScrollOffsetChanged` / `topInset`：把滚动偏移、顶部安全区传给原生，用于做原生导航栏联动（透明渐变等）。

这正是"UI 层写完、还要在平台入口挂一下"的关键一步——Android 侧通常直接在 Compose 导航图里引用 `MedalWallScreen`，而 iOS 侧需要这一层 `ViewController` 桥接。

## 数据层 ↔ 领域层 对照表

| 维度 | 数据层（DTO / data） | 领域层（Domain） |
|------|---------------------|------------------|
| 文件 | `MedalListDTO.kt` | `MedalList.kt` |
| 字段来源 | 后端 JSON 原样 | 按 UI 业务重组 |
| 可空性 | 多为 `String?`、`List?` | 全部不可空，带默认值 |
| 命名 | 沿用后端/历史 `WallMedaliItemDTO` | 规范命名 `WallMedaliItem` |
| 顶部用户 | `avatarUrl` + `wallWriting` 两个散字段 | 聚合为 `userInfo(avatar, nickname, signature)` |
| 勋章列表 | `medalEntry: List<WallMedaliItemDTO>?` | `items: List<WallMedaliItem>` |
| 分类数据 | 无 | `topicList`（接口暂未返回，空占位） |
| 依赖方向 | 依赖 domain（data → domain） | 不依赖任何数据/网络 |

**对照要点：**
1. mapper 把 `avatarUrl` + `wallWriting` 两个散字段**聚合**成 `userInfo` 对象，UI 取用更顺手。
2. 可空字段在 mapper 里用 `.orEmpty()` / `?: 0` 一次性清洗，UI 不再判空。
3. `topicList` 在领域层已预留（对齐历史 iOS 模型），但当前接口未返回、mapper 未映射，故为空。
4. 领域层完全不知道 DTO 存在——换后端字段、换网络库、换数据源，都只动 data 层。
